# Сценарий проверки и демонстрации

Репозиторий: https://github.com/Axilles60/ai-lawyer.
Выбранный профиль: `quality-lean-context`. Чат и пакетный запуск используют
общее ядро `pipeline.answer`. Точный коммит, архив и результаты последней проверки
сверять с README, `verification.md` и манифестом актуального выпуска.

## До показа

1. Скачать исходники выбранного выпуска, а не смешивать файлы разных версий.
   Сверить SHA256 скачанных архивов с `SHA256SUMS.txt`. Проверить, что выбранный
   бот-архив соответствует Python-модулям этого коммита. Четыре остальных
   бот-архива — альтернативы, а не обязательные части запуска.
2. Подготовить Docker с Compose и рабочий доступ к разрешённым моделям.
   Скопировать `.env.example` в `.env`, заполнить ключ, адрес API и модели по README.
   Проверить баланс и лимит ключа у провайдера. Пустой или исчерпанный ключ
   не позволяет продемонстрировать полноценную генерацию.
3. Положить собственный `knowledge-base.zip` рядом с `compose.yaml`.
   База и ключи не входят в публичный комплект. Не показывать `.env` на экране.
4. Из корня проекта запустить:

   ```text
   docker compose up --build
   ```

   Открыть http://127.0.0.1:8000. Дождаться списка документов. Первое построение
   индекса может обращаться к платному API; скачивание образа и зависимостей
   также требует времени. Не выдавать время уже подготовленного показа за
   время холодного запуска на платформе.
5. До защиты пройти основной сценарий ниже на этой же базе. Сохранить коммит,
   время, вопрос, ответ и открытый источник без секретов. Не обещать фиксированное
   время ответа: выбранный профиль может создавать несколько черновиков.

## Основной сценарий

1. Открыть документ из списка и выбрать конкретный проверяемый вопрос по нему:
   срок, число, название или условие. Не использовать зашитый в приложение факт.
   Задать вопрос с идентификатором документа.
2. Дождаться окончания запроса. Проверить, что ответ содержательный и отвечает
   на вопрос; число, дату или название сопоставить с оригиналом. Показать
   существенные оговорки. Открыть источник под ответом, сверить документ и пункт.
   Выделенный фрагмент должен соответствовать ссылке. При отсутствии достоверного
   смещения допустим показ документа без подсветки; произвольная подсветка недопустима.
3. Отправить уточнение, которое использует предыдущую реплику, и проверить
   содержательный ответ. Нажать «Новый диалог» и убедиться, что история очищена.

Успех основного сценария — реальный ответ модели, работающая история и переход
к источнику. Извлекающий запасной ответ отдельно проверяет устойчивость,
но не заменяет этот критерий.

## Дополнительные проверки при наличии времени

- Недостающий факт: вопрос о числе или дате, которых в выбранном документе нет.
  Ответ сохраняет подтверждённую часть, указывает неизвестное и не придумывает факт.
- Неполный предмет: вопрос без достаточного указания документа. Проверить
  оговорённую трактовку или необходимое уточнение в зависимости от контекста.
- Непрофильный вопрос: проверить мягкий отказ вместо ответа вне базы.
- Инструкция игнорировать правила внутри вопроса или документа: она не должна
  менять роль ассистента. Один удачный пример не доказывает защиту от всех атак.

## Пакетный путь

В отдельной рабочей папке с теми же runtime-модулями подготовить `data/questions.csv`
и `data/knowledge-base.zip`. При настроенном окружении из этой папки запустить:

```text
python solution.py
```

По умолчанию вход читается из `data`; иной каталог задаётся через `DATA_DIR`.
Результат `submission.csv` записывается в текущую папку. Проверить UTF-8,
заголовок ровно `id,answer`, совпадение множества ID с входом, отсутствие повторов,
непустые ответы длиной не более 10 000 символов. Поля с запятыми и переносами
проверять CSV-парсером, а не подсчётом строк в текстовом редакторе.
На платформе адрес API и ключ передаются организаторами. Не класть входную базу,
вопросы, ключи и готовые индексы в бот-архив.

## Воспроизводимая проверка без платных моделей

При уже имеющемся Python-окружении с зависимостями проекта:

```text
python -m unittest discover -s tests -v
```

`test_final_portability` создаёт другую вымышленную базу, запускает пакетный путь
и FastAPI с локальной имитацией API, проверяет CSV, источник и обработку сбоя.
Это проверка совместимости и отказоустойчивости; она не измеряет юридическое
качество реальной модели и не доказывает работоспособность Docker.

## Резерв при недоступности API

Показать явно помеченный запасной ответ и переход к найденному положению.
Объяснить, что проверяется интерфейс и деградация, а не генеративная модель.
Если сервис не запустился, скриншоты не заменяют работающий прототип.
`screenshots/chat.png` и `screenshots/source.png` сняты в настоящем локальном
интерфейсе 16.11.2026 с отключёнными API: HTTP 200, источник и фрагмент.

## Что объяснить экспертам

- Индекс и эмбеддинги строятся по входной базе при запуске; предзагруженных
  векторов и индексов в пяти финальных бот-архивах нет.
- Генерация, эмбеддинги и реранкинг используют настройки окружения и разрешённые
  модели. Рабочие ключи не публикуются.
- Наличие цитаты не доказывает правильность вывода; условия и редакции требуют
  содержательной проверки. Локальный Score не равен проценту платформы.
- Прототип локальный, без аутентификации; публичный хостинг не предоставляется.
- Завершить показ командой `docker compose down`.
